Entry point — the API
solution.py
How the outside world talks to the system
solution.py is the front door. It defines all 28 routes (14 unique operations with singular + plural paths). When a request arrives, it delegates immediately:

POST /patients → hands data to storage.py to save
POST /matchings → pulls patients and trials from storage.py, sends them to matching.py
GET /patients → asks storage.py for the list, optionally asks security.py to mask PII
GET /audit/events → asks audit.py to filter events

It contains zero business logic — only routing, input validation (via Pydantic), and response formatting.

Business logic — three separate jobs
storage.py
Where data lives
matching.py
The matching engine
security.py
Who sees what
storage.py has three repository classes: PatientRepo, TrialRepo, MatchingRepo. Each stores data in a Python dictionary (in-memory). Every time it saves something, it also calls audit.py to log the event.

It handles batch processing too — when a list of patients arrives, it validates each one separately, saves the good ones, and quarantines the bad ones with reasons.

The repository pattern means swapping these dictionaries for a real database only requires changing this one file. Nothing else touches storage directly.
Imports
audit.py models.py
matching.py is a pure function — data in, results out. It runs the three-stage pipeline:

Stage 1: Rule evaluator — checks each patient against each trial's eligibility rules using the {field, op, value} pattern.
Stage 2: Exclusivity check — blocks patients already enrolled in an overlapping trial.
Stage 3: Capacity filter — respects min/max participants per trial.

For every patient excluded, it records why — which rule failed and what the patient's actual value was. No storage, no API calls, no side effects.
Imports
models.py
security.py contains the PII masking functions. It takes a patient object and returns a copy with the name redacted ("Alice Smith" → "A. Smith") and date of birth hidden ("1985-03-15" → "1985-XX-XX").

It only reads data — never modifies, saves, or logs anything. In production this would be controlled by OAuth2 roles. For the assessment, it's toggled by a ?full=true query parameter.

Record keeping — the audit trail
audit.py
What happened and when
audit.py is an append-only event log. Every time storage.py creates a patient, rejects a bad record, adds a trial, or stores a matching result, it calls audit.append() with a timestamped event.

Nothing is ever updated or deleted — events only accumulate. The log supports filtering by entity type, entity ID, event type, and date range.

Six months later, a regulator asks "what happened to patient X?" — the answer is in this log.

Foundation — every file imports this
models.py
What the data looks like — the contract
models.py is the foundation of the entire system. It defines every data type using Pydantic v2: Patient, Trial, Matching, AuditEvent, EligibilityCriterion, and more.

Every other file imports from it. It enforces validation rules — enums for conditions and toxicity (only allowed values accepted), date checks (no future birthdays), constraint validation (min ≤ max participants).

It calls nothing and imports nothing from the project. It's the bottom of the dependency tree. To understand the system, start here.
